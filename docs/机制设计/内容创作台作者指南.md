# 内容创作台作者指南

状态：阶段 1—5 及 2026-10-16 跨年代增量 A—D 已本地实施并完成定向技术验证；所有新增 UI 仍待人工验收，正式安装与按包恢复见第 10 节。创作台用于制作本地内容，正式游戏的玩法与存档规则保持不变。阶段实现记录见[实施计划](../规划/内容创作台实施计划.md)。

## 1. 启动与工作区

在项目根目录安装锁定依赖并启动本地服务：

```bash
npm ci
npm run dev
```

打开 `http://127.0.0.1:5173/studio.html`。本轮验证环境为 Node.js 25.6.1；端口被占用时以终端显示地址为准。构建后的静态页面没有写入服务，作者入口需要本地 Vite 服务。AI 使用同一项目目录的 `npm run --silent studio <method>`，JSON 参数从标准输入传入；不能通过参数指定文件系统目录、身份或执行代码。

工作区存于忽略目录 `.studio/`。修改先成为表单，再提交为提案，经审阅应用后成为新的草稿版本。只在导出或试玩时编译为独立运行包。人物身份定义及基础地理在工作区共享；2026-10-16 起复制的剧本带独立地图快照，人物生命初态、开局状态、军政配置和事件适用范围按剧本分别设置。没有独立快照的旧剧本继续使用共享地理。请先导出备份，再做整包替换或基础升级。

## 2. 做一个第二剧本

1. 在“剧本”复制现有剧本，填写新的稳定 ID 和名称。既有作者事件的适用范围及测试随复制生成待审变更。
2. 在“人物”创建家族、人物；在“剧本状态”配置可玩资格、身份、驻地、私钱、行粮、NPC 储备及县级任职。身份文字不等于实际官职权限。
3. 在“军政配置”建立独立配置，设置地方人口、公粮、地方公款、中央公库、驻军、统帅、外交和行政关系。兵额及军粮必须有实际来源；试玩会检查人口、钱粮、公库与统帅资格。
4. 在“地图”修改既有地点坐标、道路和地区控制。生成边界只是预览，须另行审阅应用；生成邻域不是历史县界。改变控制权不自动改变行政隶属。
5. 在“事件”建立有条件、有选择及明确收尾的短链。先停用配置，再审阅启用；保存测试用例，分别覆盖完成、取消与条件不满足。
6. 每批修改提交并核对右侧前后差异；运行“校验”、隔离试玩和事件测试。预览使用实际规则和临时内存，不写入正式游戏存档。
7. 导出 `.release.json`，在“剧本 → 导入重载”校验并隔离重载。确认存档往返通过后，再决定是否将作者草稿导入工作区。

可复现示例是“江淮守望 · 架空验收剧本”：新增沈宁及验收沈氏、县级任职、地方与中央资源、驻军、控制与道路变化、带完成和取消分支的事件。它是作者配置示例，不是史实重建。运行以下局部脚本可在临时工作区重新制作并导出到 `.cache/content-studio/river-watch-546.release.json`，不会应用到你的 `.studio`：

```bash
node scripts/verify-strategic-studio.mjs
```

## 3. 人类与 AI 共用事务

```bash
printf '{}' | npm run --silent studio schema
printf '{"target":"people","query":"萧纲"}' | npm run --silent studio search
printf '{"target":"people","id":"xiao-gang"}' | npm run --silent studio read
printf '{}' | npm run --silent studio snapshot > .cache/content-studio/current-draft.json
printf '{}' | npm run --silent studio backup > .cache/content-studio/author-backup.json
```

从 `snapshot.revision` 和 `read` 的实际值生成提案；下例的版本及原值必须替换为实际读取结果：

```json
{
  "key": "author-edit-unique-001",
  "baseRevision": 2,
  "title": "补充人物小传",
  "operations": [
    {"target":"people","id":"xiao-gang","field":"biography","before":"实际原值","after":"作者修改"}
  ]
}
```

将它作为标准输入调用 `studio propose`，然后 `preflight` 传入 `proposalId`。人类可在右侧“AI 提案”审阅并应用，或仅授权这一份提案，再由 AI 调用 `apply`。写入的 `key` 必须唯一，同一请求重试复用原 key；同 key 不得改参数。版本冲突时重新读取并生成提案，不能把新 revision 直接填回旧修改冒充重新审阅。

普通提案为 1—100 项操作；支持的目标、字段、范围和事件示例以 `schema` 为准。已有基础官员中包含中文区划 ID，须完整复制实际 ID；新建 ID 使用英文、小写数字、短横线等现行格式，不改名替换稳定 ID。

## 4. 备份恢复与基础迁移

“存／备份”导出 v2 作者备份，包含完整基础包、草稿、历史、提案记录及最近调试摘要。完整调试复现内容仍从事件调试页单独导出。备份是数据，不包含资产文件。导入备份恢复的是作者草稿；历史与提案仅作来源记录，不恢复旧授权、旧回执或自动执行历史命令。

在“剧本 → 导入重载 → 草稿恢复与内容迁移”选备份或发行包，点击“预览迁移／恢复”。不选文件时，“当前工作区升级”把本地作者修改迁到当前基础包。

合并比较原始基础、作者修改和当前工作区。独立字段可保留双方变化；同字段修改、删除与修改竞争、双方新增同 ID 会列出冲突。数组按整个字段选择。先选择保留哪一侧，再次预览；冲突消除后生成迁移提案，最后在右侧审阅应用。新增字段、引用和结构也接受完整草稿验证，无法识别的字段不会静默忽略。

迁移应用会更新草稿版本、记录基础摘要并撤销其他旧授权。它不把旧运行包重新贴上新依赖标签，也不改写游戏存档锁。存在语义错误的草稿可以保留，但必须修复后才能编译和试玩；升级后重新运行所选剧本校验和事件分支测试。跨基础版本不能直接撤销历史操作，应导入迁移前备份并重新审阅。

AI 的同一入口是 `migrationPreview` 和 `proposeMigration`。可将导出的备份包装为输入文件：

```bash
node --input-type=module -e 'import fs from "node:fs"; const source=JSON.parse(fs.readFileSync(".cache/content-studio/author-backup.json","utf8")); console.log(JSON.stringify({source}));' > .cache/content-studio/migration-request.json
npm run --silent studio migrationPreview < .cache/content-studio/migration-request.json
```

预览返回 `conflicts[].scope/id/path/ancestor/current/incoming`。解决方式为 `resolutions: {local: {"冲突 id":"incoming"}, incoming: {"冲突 id":"current"}}`；冲突 id 是返回的 JSON 数组字符串，直接复制。`local` 比较旧工作区修改与新基础，`incoming` 比较导入文件与当前工作区；`incoming` 表示保留该次比较的作者修改，`current` 表示保留目标侧。`proposeMigration` 使用相同 source/resolutions，加唯一 key 及预览 revision；仍需人工应用或逐提案授权。迁移最多 10000 项差异。

## 5. 误关页面或草稿损坏

未提交表单暂存于**当前浏览器标签页的 sessionStorage**，重新加载后会提示恢复、导出或丢弃。只有基础摘要及草稿版本仍一致时可直接恢复；版本变化时导出对照，重新制作提案。浏览器关闭标签页、禁用存储或清理站点数据可能丢失此暂存；它不代替已提交提案和作者备份。超过 1 MiB 的表单会明确提示暂存失败，需拆分提交。

已保存工作区每次写入前保留三个循环恢复点，主文件和恢复点带完整性摘要；原子写入中断不会留下半份主草稿。页面不能加载草稿时仍可点击“读取恢复点”，预览内容后确认恢复。正常工作区也可在导入页查看恢复点。

恢复前复核主文件及选定检查点摘要，期间有其他写入则拒绝并要求重新预览。恢复生成新的版本，撤销旧授权，并在 `.studio/recovered-original-*.json` 保留原主文件；不会静默覆盖损坏证据。AI 可调用 `recoveryStatus` 和 `recoveryPreview`（`slot` 为 0—2）查看，故障恢复确认只允许人工界面。工作区锁、主文件或恢复点使用符号链接时拒绝访问；缺少主文件但存在恢复点时，不自动新建空工作区。

若恢复点均损坏、文件系统权限异常或锁损坏，请保留整个 `.studio`，不要删除证据重试。外部作者备份可在干净的本地项目副本中预览并迁移；本工具不接受任意目录恢复或自动修复锁文件。

## 6. 支持范围与安全边界

| 内容 | 已支持 | 边界 |
| --- | --- | --- |
| 完整运行包 | `fynbc-content-package` schema 1、`three-realms-v1`、33 张表 | 必须匹配规则与本地资产；不执行包内代码 |
| 发行包 | v2 携带原始基础；v1 同环境重载兼容 | v1 跨基础迁移需匹配的原基础或原版本作者备份 |
| 作者备份 | v2 摘要校验；v1 可读 | v1 没有外层完整性摘要，仍检查基础包及完整草稿；未识别运行表结构拒绝迁移 |
| 跨版本迁移 | 当前支持的 schema/profile 内作者数据三方合并、重新编译 | 不是任意旧规则执行器；新机制或未知 schema 需专项适配 |
| 游戏旧档 | 沿用既有精确内容锁与官方版本兼容桥 | 本阶段不迁移游戏存档；自定义包旧档仍需原内容与规则 |
| 文件输入 | 普通 JSON；导入／迁移 16 MiB，普通请求 1 MiB；最大深度 64、500000 节点 | 拒绝危险键、访问器、非有限数值、非法 UTF-8、额外作用域及未知字段 |
| 资产 | 本地文件清单、长度、摘要及精确依赖核对 | 拒绝绝对路径、父目录路径、网址、重复路径及符号链接；不下载或执行外部资产 |
| 恢复 | 三个本地检查点、作者备份合并、当前标签页表单暂存 | 摘要用于检测损坏，不是作者身份签名；没有云备份或跨机器同步 |
| 大名单 | 人物目录及可玩名册每页 40 项；可搜索；肖像进入视区后加载 | 沿用 24×1024×1024 像素上限的肖像缓存；不是字节数或总进程内存上限 |
| 取消 | 可放弃表单、退回提案、取消文件选择及不应用预览 | 已启动的隔离试玩／编译暂不提供中途取消；写入进行时等待原子事务返回 |

HTTP 写入仅允许 loopback、匹配的 Host/Origin、当次服务 token 和 JSON POST。AI 身份由 CLI 固定，不接受输入伪装为人类。发行包没有脚本插件或任意文件读取能力。不同作者间使用迁移入口合并；“生成导入提案”是同基础整份作者草稿替换，审阅时尤其注意删除、共享地理和其他剧本的变化。

本轮标准样本规模：325 人、1041 条本地资产清单，官方剧本 v2 发行包紧凑 JSON 为 3284902 字节。测试用时是当前环境的局部执行记录，不是性能承诺；未测试万级内容库、浏览器内存峰值或长局性能。

## 7. 人工验收顺序

1. 人物搜索与翻页、名册勾选、切人、肖像及固定操作区。
2. 编辑但不提交，刷新同一标签页，检查暂存恢复；另一个作者更新版本后，确认阻止直接恢复旧表单。
3. 导出备份，改动同字段，导入并解决冲突，逐项核对右侧差异和作用范围。
4. 在测试项目副本中预览及恢复检查点，确认原文件保留及旧提案需重新审阅。
5. 按第 2 节完成第二剧本制作、事件测试、校验、隔离试玩、发行包导出和重载。

这些步骤尚待用户人工验收；代码测试与构建结果不替代视觉和交互验收。


## 8. 跨年代人物与地图（阶段 B，2026-10-16）

阶段 B 提供共用数据和运行规则；阶段 C 已补齐人物生命状态及行政节点增删的专用表单，见第 9 节。也可通过同一 CLI／服务提出结构化变更，再在创作台审阅；AI 无权直接应用。先处理已有工作区的基础迁移审阅，再复制剧本，勿直接替换运行中的世界。

- `scenarios.life` 为人物 ID 到 `{presence,health,deathYear,source}` 的映射。`presence` 为 `active/dead/unborn/excluded`；在世健康 1—100，其他状态为 0，只有已故状态可填已故年份。来源必填，可明确标为架空。空对象开启出生年筛选；`null` 保留旧分支。可玩人物和实际任职必须与生命状态一致，死亡不是取消勾选可玩；修改时一并调整默认人物、可玩名单和职位。
- 健康是人物持有的状态值；初值只作用于新开局。已故年份为开局资料，不触发历史强制死亡；未出生人物不按预定日期自动加入。亲缘身份保留，未参与本局不等于已故。
- 通过 `mapTemplate` 获取完整候选快照（参数为 `scenarioId`），以 `scenarios.map` 作为变更字段提交。已有地图入口会按当前快照编辑名称、坐标和道路；清楚核对工具栏的“剧本地理／共享地理”及右侧变更范围。
- 新地点同时提供地图锚点、现有地形模板 ID、道路、`city:<地点ID>` 行政锚点及完整州郡县上级、军政 `cities` 初值和来源。新人口是作者开局存量，不是继承模板县的人口；公库拨款、兵员和行粮仍走原有来源规则。
- 行政节点用 `from <= 开局年 < until` 的有效期，并注明出处或设计假设。跨年代复制后须重新核对有效期和父级；系统不自动把 546 年资料包装成另一年的史实。
- 增删地点后通过 `generateBoundaries` 携带 `scenarioId` 生成预览，把返回边界放入本剧本地图并审阅。生成的是陆地裁剪示意县域。移除地点前清理道路、驻地、军队、事件和军政资源引用；不能仅隐藏图标。

每轮应用后先 `check`，再 `preview`（建议先用一日）及导出重载。当前仍保留建康基础旅行锚点和既有地图范围。正式安装库、前后台切换内容包及按存档定位包属于阶段 D，不能把隔离试玩视为已安装到正式游戏。


## 9. 跨年代制作表单（阶段 C，2026-10-16）

以下是当前可用操作；UI 仍待人工验收。已有工作区先预览基础迁移并审阅，再复制目标剧本。所有“生成提案”只产生待审变更，核对右侧前后值并应用后才写入草稿。

1. 在“剧本”复制开局，进入“政权开局”建立独立政治、军政与地图配置。调整年份后核对人物参与和“地点区划”的节点有效期。参考配置来自基础包，必须自行考订，不能当作另一年代史实。
2. 逐国填写国号、简称、颜色、制度模板、首都、君主和实际执政者；称谓不授予权限。新增国家须使用空闲稳定 ID，首都不能已有其他首都或开局驻军；新中央钱粮从 0 开始。移除国家须选明确接收者，审阅钱粮、人物、驻军、领地及外交／战争移除；合并超过中央容量会拒绝。
3. 在“人物”的当前剧本开局配置设置效忠、驻地、可玩、职位与私财，补充生命／参与状态、健康、四项基础能力和性格来源。非活动人物联动撤销可玩和已配置任职／统帅／继任人；默认人物、君主和执政者先替换，继承基础军队时先独立配置军政。生命与联动字段进入原有暂存队列，可刷新恢复后继续审阅。
4. “政权开局”可指定君位和执政继任人，开局检查真实资格；亲缘承统不另填国号，非宗亲按既有承统规则填写新国号。留空沿用原继承逻辑，后续仍由真实模拟决定，不按历史日期强制换朝。
5. “地点区划”新增州／郡／县节点，明确上级、有效期和来源；新增县治地点时选择已有地形模板、坐标、归属、上级郡及明确人口／公粮。提案会带连接道路和重建的示意县域，不能把生成边界作为历史疆界。既有地图页编辑坐标、道路和军政资源，行政修改集中到节点入口，旧行政覆盖在同一变更中归入节点。
6. 移除地点时先处理首都与相关事件，再选择人物和军队的转移地点；转移军队要求本国实控。提案包含驻地、职位、道路和县治节点变更，不只是隐藏图标。保留建康基础旅行锚点，节点删除先转移下级，移除道路后须保持可达。
7. 选择是否启用侯景原生事件。不同年代默认不启用，勾选后仍校验所需国家和人物。作者事件可用“公历年不早于”和“迁驻朝廷”；迁驻复用实际规则，执政者须已经抵达且控制目标地，中央公库支出 100 钱。行动不能直接传送人物、修改作者数据或绕过实际办理权。
8. 应用后运行校验，再做一日隔离试玩、事件调试、完整发行包导出和导入预览。单独运行包用于运行，完整发行包才携带作者数据和基础用于后续创作。两者都不代表已安装进正式新游戏，正式安装与按存档找包使用第 10 节的阶段 D 入口。

能力配置是基础值（各 0—30，默认 8），经历、培养、遗传、健康和已获成长另算，最终上限沿用 40；不能把期望总能力直接当作基础值。性格只开放现有九项，贪婪／正直及节俭／慷慨互斥；`traits: []` 明确无作者性格，`null` 继承原规则。独立的经济特征等仍由原规则计算。配置只影响所绑定内容包，不回写正在运行的世界或重置旧档成长。

AI／CLI 使用同一 Schema 和制作计划：

```bash
npm run --silent studio schema
npm run --silent studio authoringTemplate <<'JSON'
{"scenarioId":"my-era"}
JSON
npm run --silent studio authoringPlan <<'JSON'
{"scenarioId":"my-era","baseRevision":12,"command":{"kind":"mapDates","from":558,"until":559}}
JSON
```

示例 ID 和 revision 要替换为实际工作区值。`authoringTemplate` 只返回参考配置；用 `initialize` 制作命令带回 `politics/strategy`。`authoringPlan` 支持 `initialize/addRealm/removeRealm/setPresence/addSite/removeSite/addNode/removeNode/removeRoad/mapDates`；其完整字段可从 `schema.authoringCommands` 读取。计划返回普通 `operations`，将它们原样放进既有 `propose`，之后 `preflight` 并人工审阅或逐提案授权；计划本身不应用，过期 revision 会拒绝。

一般表单同样可用结构化字段操作编辑 `scenarios.politics/personSetup/succession/life/map/strategy`。大批人物调整可用经过完整校验的 `scenarios.states` 快照；先读前值，不用省略字段覆盖未知内容。大快照的撤销会核对整份人物状态，存在后续编辑时需重新审阅，不能强行覆盖。


## 10. 安装与正式游玩（阶段 D，2026-10-17）

UI 尚待人工验收。游戏入口 `http://127.0.0.1:5173/`；作者入口继续用 `/studio.html`。

1. 在创作台迁移已有草稿、校验并隔离试玩，再导出运行内容包或完整发行包。旧发行包若显示规则／资产依赖不匹配，请在创作台审阅迁移并重新导出；作者备份不能直接安装。
2. 游戏主菜单进入“剧本藏库”→“导入内容包”。先查看实际开局校验和剧本摘要，再“确认安装”；这一步不改当前行记。完整发行包还核对其资产清单与当前游戏，不能借导入安装任意脚本、下载额外资源或缺失资产。
3. 选择已安装内容；系统先备份当前实际进度，再刷新到所选内容。随后“开始新游戏”选择包内剧本及人物，确认开局。人物、国家、地图、规则和保存使用同一内容包。同包的多个版本分别列出摘要，不覆盖旧版本。
4. 保存后关闭并重新打开游戏，按最近行记的原摘要恢复；从“行记”选择其他内容的存档也会先定位原包。沿用一份手动、三份自动和一份切换前备份，所有内容共用槽位。长期保留多个剧本进度时分别导出行记和对应原内容包。
5. 缺包或坏包会进入恢复页，原行记不变。导入它绑定的原包并重试，或导出备份／选择其他有效行记；不会拿官方新局替代。内容只装在当前浏览器，账号云存档不会自动同步原包，换设备须重新导入。
6. 切换中断时可重试，或“取消切换并恢复原行记”；系统保留的是切换前的实际快照，包含尚未更新到手动槽位的进度。待完成记录成功后才移除，其他中断记录可在藏库取消。切换记录绑定原账号，换账号后不会自动导入上一账号进度；可切回原账号重试，或取消本窗口切换。
7. 移除前先“导出原包”。当前使用中、仍被当前可见行记或待完成切换引用的版本不能删除；先自行整理相关行记并确认备份。重新导入完全相同且校验通过的原包可修复损坏的本地安装记录。

自定义包精确绑定规则及资产版本。作者草稿迁移、安装包更新和玩家存档迁移是三个过程：迁移作者内容不会把旧玩家进度自动转换到新摘要；旧行记依赖不匹配时，应使用匹配的游戏版本，原包与原行记继续保留。官方旧档只走已验证的兼容路径，不移除内容锁或放宽世界校验。

测试环境若再出现读档报错，在“行记”或恢复页点“复制存档版本信息”，将文本粘贴到对话即可，不需要寻找旧诊断页或提供存档正文。该信息包含四项内容锁、槽位与日期，用于精确识别缺包、规则版本或损坏问题。

人工验收重点：两个包与同包两个版本的选择、绑定名称和地图、新游戏确认、五槽与跨包读档、重开恢复、缺包导入原包、失败提示及取消恢复。代码／存储测试不等于视觉和交互验收。
