# 风云南北朝：网页游戏落地方案

版本：0.1｜2026-09-22｜状态：用户已授权开工，第一阶段骨架已实施，UI 待人工验收

## 1. 产品定义与决策边界

制作一款桌面浏览器优先、单人、可暂停与调速的南北朝人物大战略游戏。全国战略地图是主场景；玩家通过人物、家族、官职、资产与军队参与持续运行的世界。冒险者、官员、将领、统治者共用同一套世界和规则。大模型增强人物交流，世界规则独立运行。

依据：[原讨论《评估游戏可行性》最后一轮修正结论](https://chatgpt.com/c/6ab13b34-7030-83ec-b8be-5174696c6b3a)。本轮已明确产品形态为网页游戏。

**必须保留：**全国及必要周边地图；有质感的地形与政治地图；人物成长及家族关系；官职升迁；战争与建设；具有时间和路线约束的人物移动；南北朝制度与历史事件。

**本提案的默认选择：**独立 Web 应用、桌面键鼠优先、单人本地模拟、首版一个历史开局。暂不制作多人持续在线世界、移动端完整操作、独立战术战场、自由摆放的城市建设、三维人物捏脸。此处是设计建议，不能视为用户已经批准实施或发布。

开局年份暂以 **546 年**为考据候选，用于组织历史资料；具体日期、政权范围和制度截面在历史资料审查后冻结，不把候选年份当作已完成的史实数据库。引擎与数据包分离，调整开局不重写系统。

## 2. 首个可玩版本应交付什么

首个可玩版本需呈现完整游戏形态，而不是只完成地图查看器或几个互不相通的身份演示。

| 项目 | 首个可玩版本目标 | 后续增加 |
|---|---|---|
| 全国地图 | 全图可浏览、选择地区、寻路和行军，政治归属随模拟变化 | 提高局部地貌、城邑与季节表现 |
| 世界规模 | 暂按 400—600 个战略地区、2,000—3,000 名在世人物规划 | 性能通过后扩展地区和人物数量 |
| 人物 | 年龄、健康、性格、能力、信仰倾向、关系、婚姻、家族、经历 | 丰富特质、成长路线和专属事件 |
| 身份 | 冒险者、地方官、统治者三个开局；将领作为兼任职责 | 更多中央职位和特殊职业 |
| 人生延续 | 死亡后依既定规则转入可继承的家族成员，无继承人则结算 | 更复杂的宗族分支与继承争议 |
| 官僚 | 推荐、任命、赴任、履职、考核、罢免；两套有实质差异的制度配置 | 更多政权与时期的制度特例 |
| 经济建设 | 户数、粮、财富、劳力；庄园、城邑、跨地区工程 | 更丰富的商品与产业 |
| 战争 | 宣战条件、动员、行军、补给、交战、围城、议和 | 更多兵种、战术倾向和外交条款 |
| 内容 | 一套历史开局、约 20—30 种通用事件模板、3 条重点条件事件链 | 扩充人物传记与地方内容 |
| AI | 基础版本不用 AI 也能完整运行；后续接入请求、举荐、谈判 | 更丰富的方案组合与人物表达 |

上述数字是范围预算和压测假设，不是史实数量、性能承诺或发行版内容承诺。历史边界未查清时允许使用明确标注的近似地区，不以现代行政边界冒充古代边界。

## 3. 用同一条玩法链贯通身份

核心循环：**观察局势 → 选择人物目标 → 调动资源与关系 → 移动或委托 → 结算结果 → 改变人物和世界 → 获得下一次机会。**

首条贯通场景采用“边地缺粮”，以下均为机制测试情境，不指称具体史实：

1. 边境战事提高运输风险，地方粮仓出现缺口，官员产生送信与护送需求。
2. 冒险者接受运粮委托，比较近路、绕路、关隘通行和随从开支；途中通过会面取得支持。
3. 完成委托后获得酬劳、经历和举荐机会；失约会留下债务或关系后果。失败仍可继续人生。
4. 符合条件并获得任命后，人物需实际赴任。接管的是职位权限和公共账目，个人资产保持独立。
5. 官员选择征粮、购买、借调或修复运输设施。每项选择改变地方生产、民意、家族利益和军事供给。
6. 统治者通过任命、拨款和军事授权处理危机；将领收到命令后，根据忠诚、利益和实际条件执行、拖延或拒绝。
7. 议和、失地或权力转移改变财政与职位，再影响原来的冒险者、家族及地方居民。

普通人物进入官场需要资格、空缺、推荐与任命；成为统治者需要继承或权力转移规则成立。不能用同一条经验值升级表处理。测试可以分别使用三种身份存档，但还必须验证同一人物获得和失去职位、成为或失去统治者身份后的权限变化。

## 4. 系统对象与核心约束

| 对象 | 必要信息 | 必须保证 |
|---|---|---|
| Character 人物 | 稳定 ID、生死、年龄、能力、特质、家族、位置、关系、活动 | 死者不能行动；位置与活动相容 |
| Family 家族 | 成员、亲属关系、声望、家产、继承规则 | 家产、私产、公共资源分账 |
| Office 官职 | 所属政权、管辖、任职者、任命者、权限、有效期 | 离任撤销权限；兼任按制度校验 |
| Polity 政权 | 名义统治者、任命与财政权、制度、辖区、继承状态 | 名义地位与实际控制可以分离 |
| Region / Site 地区与地点 | 地形、人口、产出、城邑、庄园、寺院、归属 | 地理 ID 不因行政隶属变化而重建 |
| Army 军队 | 供给来源、调动权、指挥官、兵员、位置、补给 | 资源出资者、发令者与带兵者分离 |
| Journey / Order 旅行与命令 | 路线、进度、耗时、收件人、失效条件 | 人物、书信、军令均不能瞬达 |
| Agreement 协议 | 当事人、承诺、条件、期限、履约与违约结果 | 对话只有经规则确认才能成立协议 |
| Event / Belief 事件与认知 | 客观结果、知情人、来源、主观解释 | 传闻与谎言不能覆盖客观事实 |

原型中保留一个权威世界状态。所有玩家、NPC、脚本和 AI 行动走同一个入口：提出指令 → 校验生死/位置/权限/资源 → 预留必要资源 → 排入日程 → 执行时再次校验 → 原子结算 → 记录事件 → 通知已知情人物。

长时工程采用“预留—消耗—释放”账目，取消和失败依规则退还未消耗部分。死亡、罢免和政权更替触发相关任务重算；不得靠删除人物清除历史引用。

## 5. 南北朝机制怎样进入玩法

采用共用规则与带生效时间的制度数据。以下是拟实现的机制模型，具体名称、适用政权和年代需逐项考据。

| 系统 | 需要实现的机制 | 首版控制方式 |
|---|---|---|
| 选官与门第 | 出身、家族地位、推荐、品评、经历与军功影响资格和任命偏好 | 候选资格与任命者选择分开，不照搬考试升级 |
| 政治权力 | 皇帝、权臣、地方官和将领掌握不同权限；支持关系影响执行 | 每个关键决策显示谁可授权、谁负责执行、谁可能阻碍 |
| 土地与财政 | 土地和户口产生粮与财富；制度和控制力影响征收 | 统一核算单位，史实支持、估计和平衡参数分别标注 |
| 军事 | 兵源、供给、动员权限与忠诚受制度影响 | 先做少量兵种；地区被占领不自动等于法理归属改变 |
| 宗教 | 寺院具有地点、代表人物、资产和支持关系 | 访问、资助、求学、赈济及资源争议进入事件 |
| 历史事件 | 人物、职位、冲突和日期窗口共同决定是否触发 | 前提已被改变时转为变体或不发生，不强制复原历史 |

史料制作需记录到字段：来源、页码或条目、时间范围、可信程度、冲突说明、采用理由。未知官员使用明确的生成身份，不让模型补出的姓名成为“史实人物”。地名、边界与人物资料先审查年代覆盖和使用条件，再纳入数据包。

## 6. 地图：画面细节与模拟精度分开

使用 Three.js 构建有起伏的三维地形，以斜俯视战略相机呈现；界面使用网页组件覆盖在地图之上。全国基础地形始终存在，近景细节分块加载。

| 距离 | 玩家主要看什么 | 实现重点 |
|---|---|---|
| 远景 | 政权、国名、边界、战线、山川轮廓 | 政治着色与地形混合、国名字号和标签避让 |
| 中景 | 行政区、城邑、道路、关隘、军队、旅行路线 | 点击选区、动态边界、路线与军队标记 |
| 近景 | 城邑、庄园、寺院、山口、森林和水面 | 地形法线、代表性模型、实例化植被与氛围 |

地理数据分三份：用于观看的地形与材质；用于规则计算的战略地区；用于旅行、运输与通信的节点网络。地区由稳定 ID 关联，政治归属通过颜色映射更新，不重建整张地图。

生产顺序：全国低精度底图 → 选一个包含平原、山地、河流、城邑的样板区域 → 用户确认美术标准 → 推广到全国。样板区只用于校准表现，全图始终纳入模拟。

路线成本综合行程、地形、季节、通行条件和风险。旅行队与军队使用不同参数；前方关隘易手后，队伍在下一决策节点重新规划，不能瞬移或穿越封锁。大军补给使用同一运输网络，按周期计算运力与消耗，不逐辆模拟粮车。

“质感对齐 CK3”是人工验收目标，拆成地形层次、材质统一、政治边界可读性、缩放连续性与标签秩序。不能以技术上能显示三维地图视为完成美术要求。

## 7. Web 技术架构

建议使用 **TypeScript + React + Vite + Three.js + Web Worker + IndexedDB**。浏览器为主要运行环境，不把桌面引擎导出包作为默认路径。具体依赖版本在开始实施时锁定。

| 部分 | 职责 | 边界 |
|---|---|---|
| React 界面 | 人物、官职、军队、账目、事件、行动预览 | 读取世界投影、提交指令，不直接修改世界 |
| Three.js 地图 | 相机、地形、政治颜色、选区、标记和动画 | 不负责经济、战斗或人物决策 |
| Simulation Worker | 时间、人物活动、财政、政治、战争与规则 NPC | 世界状态唯一写入者，避免主线程长任务 |
| Shared Core | 数据类型、校验、规则、寻路与固定种子随机数 | 纯 TypeScript，可在 Node 中做无画面长期模拟 |
| Content 数据包 | 地图、制度、人物、事件、建筑、翻译与来源 | 有版本、有引用校验，与运行状态分开 |
| Persistence | IndexedDB 快照、自动存档、导入导出、迁移 | 保存完整随机数状态、任务队列与版本 |
| 可选 AI 服务 | 鉴权、限额、模型调用、日志最小化 | 密钥只在服务端；不成为世界运行依赖 |

Three.js 的 WebGLRenderer 使用 WebGL 2；官方仍将其作为纯 WebGL 2 应用的推荐选择。本方案因此以 WebGL 2 为首版基线，WebGPU 留作后续评估，不将其作为进入游戏的必要条件。[Three.js 渲染器文档](https://threejs.org/docs/pages/WebGLRenderer.html)、[WebGPU 说明](https://threejs.org/manual/pages/webgpurenderer)

主线程仅获取可见地区、已打开面板与重点人物的增量数据；不能每个模拟日把全世界序列化给 React。地图每帧渲染，界面按变更更新，模拟独立推进。首版先用一个 Worker，避免过早引入跨 Worker 同步复杂度。

全国规则分频执行：旅行和战斗按日；普通人物计划按旬或受事件触发；经济和工程按月；年龄、制度检查等按相应周期。远方同样执行财政、战争、任命和继承，不能在玩家抵达时才临时生成结果。

同一天内部明确固定处理顺序和 ID 排序，资源用整数最小单位计算。暂停、加速和读档不改变规则顺序。后台标签页默认暂停；返回时继续存档时间，不按现实离线时长跳过关键决策。

服务端不承载首版单人模拟。首个交付可作为静态网站运行；以后增加 AI 网关和可选云存档。若未来要求多人或世界离线持续运行，需另立服务端权威模拟方案，不能视为简单增加登录功能。

## 8. 存档与浏览器可靠性

IndexedDB 支持结构化数据，且可在 Web Worker 使用；浏览器存储仍受配额及清理策略影响，因此本地存档必须配套导出文件。[IndexedDB 文档](https://developer.mozilla.org/en-US/docs/Web/API/IndexedDB_API)、[存储配额与清理规则](https://developer.mozilla.org/en-US/docs/Web/API/Storage_API/Storage_quotas_and_eviction_criteria)

- 每次保存固定模拟步的完整快照，附带存档格式、规则版本、内容版本、随机数状态、待办任务与校验值。
- 保留至少三个自动存档槽；新快照写入成功后再更新当前指针。配额不足时明确报告保存失败，禁止显示“已保存”。
- 提供手动保存、导出与导入；申请持久存储只能降低风险，不能替代备份。
- 同一存档只允许一个标签页持有写入权，其他标签页只读或提示切换；关闭与崩溃后可恢复锁。
- 升级前备份旧档；兼容版本运行迁移，不兼容时给出明确提示，不静默丢字段。
- 首次完整加载后再提供离线缓存；静态资源与内容版本成套更新，避免旧代码读取新数据。

## 9. 界面与信息表达

布局建议：顶部为日期、速度、待办与关键资源；左侧为当前人物及身份；中央地图；右侧为选中人物/地区/军队面板；底部为事件和行动队列。

每个行动在提交前回答五件事：谁执行、需要什么权限、消耗什么、何时生效、可能有什么后果。不能执行时显示具体缺失条件，例如“任命尚未送达”或“你没有该军队的调动权”。

资源归属以私产、家产、任职可支配公共资源分别展示。玩家可以知道全国公开政权边界；远方军队、私人关系和秘密按情报来源展示，并标记消息时间，避免界面泄露人物本不知晓的信息。

重大事件可暂停，普通事件合并通知。每项重要结果支持查看来源：任命者、粮食消耗、关系变化的事件、未执行命令的原因。让复杂性可解释，而不是靠弹窗数量表现复杂。

前端视觉和操作体验全部由用户人工验收，提供本地入口与明确的验收场景；不采用 computer use、浏览器自动化或截图比对进行 UI 验收。

## 10. AI 接入方案

AI 先覆盖拜访、举荐请求、条件交换与书信四类交互。输入只包含当事人可知信息、近期相关经历、合法行动集合和资源约束。

流程：自然语言 → 结构化提议 → 规则校验 → 玩家确认明确的条件与代价 → 生成游戏指令 → 正式结算 → 表达回应。不可用的行动说明原因，不凭一句台词新增游戏能力。

提议必须带人物 ID、相关状态版本、期限和唯一请求号。等待模型时世界可能已变化，返回后需重新检查任职、生死、位置和资源；重复请求不重复结算。记录已采用的结构化结果，使回放不依赖模型再次生成相同文本。

规则 NPC 持续处理全国事务。AI 只在重要互动时调用，设置每局及每真实游玩小时预算；超时或断网退回明确标注的固定选项。正式提供云端 AI 前实现服务端限额与授权，不将模型密钥放进浏览器。

价值验证采用同一任务的模板版与 AI 版人工试玩：是否出现不同可执行方案、是否准确引用既往事实、是否让玩家改变策略。费用按实际 token、重试和总调用量记录；本方案不使用未经核验的厂商报价推算承诺成本。

## 11. 实施顺序、产出与验收门槛

依赖顺序为 A → B → C → D → E。地图素材考据可以与程序工作并行，但必须先统一地区 ID 与数据格式。以下工作量是提案估算，尚未根据实际团队能力校准。

| 阶段 | 可交付成果 | 验收门槛 | 参考投入 |
|---|---|---|---|
| A 设计与资料冻结 | 地图覆盖范围、候选开局审查、对象与权限表、样板美术标准、目标设备 | 已确定主要数据来源、缺口及验收设备，不存在阻断全图制作的数据问题 | 2—4 人周 |
| B 全国骨架 | 全图、三档缩放、选择地区、Worker 时钟、旅行、政治着色、存读档 | 远方也运行；人物不能瞬移；关闭后可以恢复；地图样板由用户人工确认 | 6—10 人周 |
| C 身份贯通 | 委托、关系、任命赴任、收支、建设、基础战争、继承与权力转移 | 三种开局均能改变同一世界；同一人物身份变化后权限正确；完成边地缺粮场景 | 12—20 人周 |
| D 历史与稳定性 | 一套经审查的历史开局、制度差异、事件链、历史记录、数据制作工具 | 长期模拟与存读档验证通过；关键史实有来源；用户完成玩法验收 | 10—18 人周 |
| E 表现与 AI | 全国美术扩展、音效、信息层级打磨、受控 AI 交流 | 用户确认视觉和体验；AI 不越权；断网可继续；调用预算可控 | 10—20 人周 |

B—C 为首个功能原型，D 为可验证历史玩法的 Alpha，E 后仍需内容扩充、兼容性、平衡与发行准备，不直接视为完成商业版。

总量约 40—72 人周，主要用于受控原型/Alpha；地图与内容返工可能继续增加投入。2 名全职开发的纯算术容量约为 20—36 周，但仍需要历史策划和技术美术参与，不能直接当作日历交付承诺。个人加 AI 应按实际每周投入重新排期，不沿用多人团队日期。

职责最低覆盖：产品与系统策划、模拟程序、Web 地图与界面、历史资料与内容、技术美术。人员可以兼任，但地图美术和史实核查不能假设已由 AI 自动解决。

第一轮实施只推进 A 与 B 的起步任务：冻结 ID 和命令约定；创建纯规则内核及读档测试；导入覆盖全国的粗地图；建立 Worker 与 UI 通信；实现旅行和政治归属更新；制作一个地图质感样板。每项交付均应可独立检查。

## 12. 必要验证与继续投入条件

性能数值是待验证目标。A 阶段先登记实际基准设备、浏览器、分辨率和画质，之后同条件比较；未定设备前不宣称达标。

| 范围 | 目标 / 检查 |
|---|---|
| 基础规模 | 常规档 600 地区、3,000 在世人物；压力档 1,000 地区、10,000 在世人物，仅用于发现瓶颈 |
| 地图 | 1080p 中等画质目标稳定 30 FPS，60 FPS 作为优化目标；用户人工检查缩放、标签和操作 |
| 加速模拟 | 常规档目标至少 30 游戏日/真实秒；普通单日耗时 P95 ≤20ms，月度重任务分片并单列耗时 |
| 首次下载 | 首屏必要压缩资源目标 ≤20MB，高清模型和材质后载；不能承诺无等待即玩 |
| 内存与存档 | 常规档总内存预算先按 1GB；存档目标 ≤20MB、保存目标 ≤2 秒，实测后调整资产或日志策略 |
| 规则一致性 | 无未经定义的负库存、重复扣费、重复任命、死亡行动、失效权限及悬空引用 |
| 存读档 | 同版本、同种子、同指令序列下，连续运行与中途读档后的核心世界校验一致 |
| 长期运行 | Alpha 对至少 20 个固定种子运行 50 游戏年；测试继承、迁移、战争、人口与财富趋势 |
| 异常场景 | 在途死亡、赴任前罢免、粮仓被占、重复命令、损坏存档、配额不足、AI 结果过期 |
| 历史内容 | 关键人物和职位引用有效，出生死亡与任职时间相容；事件条件被改变后不会强制复位 |

程序验证在纯内核、Worker 消息协议、构建及服务接口层进行；不以自动化浏览器执行 UI 验收。性能趋势可通过内核基准及应用内诊断面板记录，图形与浏览器使用体验由人工确认。

继续投入的三道门：B 验证地图表现方向与浏览器运行预算；C 验证不同身份确实通过同一世界相互影响；D 验证长期模拟稳定且历史机制产生可解释的取舍。门槛未过时先调整对应模块，不用扩大内容数量掩盖问题。

### 实施追记 · 2026-09-22

上述“本轮”指方案设计轮次；用户随后明确要求“开工”。已按本文方向建立 React + Three.js + Worker 的本地可运行骨架，覆盖全国地理底图、34 个地点的旅行网络、逐日推进、三个后台行旅与存档恢复。当前仍是 B 阶段早期成果，未完成完整战略地区划分和历史开局考据，不代表 B—E 全部验收通过。

构建和 16 项非 UI 测试通过；视觉、操作、浏览器兼容性及大规模性能待人工或后续专项验证。入口、当前功能和数据来源见 `README.md`。没有初始化 Git、推送或公开部署。

### 地图迭代 · MapStage 参考

用户反馈首版地图过于粗糙，并指定参考 MapStage。已把地图渲染层调整为 MapLibre GL JS + Mapterhorn DEM + OpenFreeMap 矢量自然地理：以真实高程生成海拔设色、山影与三维地形，以分级水系、透明势力色、平滑示意边界、近景城邑和分层标签构成战略地图。原 Three.js 程序化山丘方案停止使用，规则 Worker 与存档格式保持不变。

新增平面/立体切换，行旅纪事默认收起以扩大地图视野。在线地形按视野请求，数据来源署名可见；在线加载失败时明确提示，并保留本地 Natural Earth 备用层。此项调整意味着高清地图需要网络，不能继续宣称地图完全离线运行。

地图中不显示现代道路、城市名称或行政边界；政权疆界仍是开发示意，尚未完成 546 年考据。参考项目的 MIT 许可与数据来源记录已保留。构建及 22 项非 UI 测试通过；本地预览使用固定来源代理加载在线瓦片，地图 Worker 独立打包。视觉效果、浏览器渲染与加载体验仍由用户人工验收。

### 546 年区划与建设追记

用户确认 546 年开局。地图新增州、郡（尹）、县、城市四种语义：前三者描述行政隶属，城市是唯一公共营建对象；家族庄园是独立家产，不随城市治理权自动取得或消失。首批细化建康、长安、邺城周边，共 53 个城市／县治、63 条设计道路、9 组有来源的郡级索引。史籍名称与生成色块分别标注证据，不将较早地志直接声称为 546 年全国复原。

庄园主宅与附属建筑、城市营建、工期、周期收益及 v1 → v2 存档迁移已实施。城市治理权暂按限制开放；当前未仕角色无权营建城市，可经营庄园。官职授予、家族继承尚未实施。完整史料范围、规则与人工验收场景见 README。

### 领地层级纠正

用户指出城市邻域分区无法体现独立领地层级，也不能还原历史疆域变化。根因是此前由城市点生成面片，再按文字隶属合并描边，把行政实体、控制权与几何混为一层。现已接入独立政权—州—郡／尹—县—城市实体树及逐级选择，但现有边界仍为示意。完整历史复原须独立考据边界版本、行政关系时间区间和军事控制事件；目前只有两条城市攻取记录，不能据此宣称已还原全国疆域演变。

## 完整游戏推进基线 · 2026-09-22

用户要求整体对齐 CK3 的完整性与成熟度。现阶段不能认定完成：人物库只有 11 位，地图行政边界仍有示意数据，社会系统没有婚姻、生育与死亡，尚无成体系的政治经济军事。既有 87 项检查验证的是已有原型，不等于发行验收。

对齐的是系统彼此影响、决策有反馈、失败仍能继续与家族长期延续；不照搬中世纪封建制度，不将新增平衡数值写成南北朝史实。资料参考 CK3 官方介绍及 Roads to Power 官方行政玩法介绍。

### 本轮实施主线与边界

先贯通公共财政、城市生产与秩序、任职与授权、动员与补给、行军交战围城、议和与军事控制、事件决策，并整合为政务入口。保留既有限时教学局和存档；历史沙盒独立标记、禁止通过读档误改旧局。建设必须区分城市公款与家族私产。战争只改变实际交战的城市控制，不能自动改变整州郡法理边界。初始城市归属及经济人口均为当前剧本的玩法数据，军事过程为分歧历史模拟。
